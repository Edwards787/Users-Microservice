# Main problems encountered
## Problem 1
### Description:
Some team members misunderstood what design patterns to apply when writing their endpoints, and it led to their code being cluttered and difficult to read.

### Reaction:
Once they figured out what design patterns to follow when implementing endpoints, they had to refactor them to fit the specified design patterns, however their design patterns changed several times throughout the duration of our project, so they had to refactor some code several times.
## Problem 2
### Description:
Towards the end of the sprint, we received feedback stating that some of our design patterns do not actually follow the notebook implementation. Therefore, we came upon a problem that not only we would need to re-do some of the classes to follow the needed implementation (i. e. builder classes), but also refactor all of the endpoint to follow it.

### Reaction:
We will change it during the next sprint (as this happened on the last day of the current sprint) and will try to be more cautious during the next sprints. I.e. not implement anything before being 100% sure that it should be there.
## Problem 3
### Description:
Towards the end of the sprint, we have tried to test HTTP requests using WireMock, as it was mentioned in the lab manual. However, adding dependency for wiremocks so that our project could use it became a problem. For some reason, it did not work and it was stopping our progress as we could not test endpoints that access other microservices.
### Reaction:
We have decided to, for now, leave testing other endpoints for later and take

## Problem 4
### Description:
We configured the pipeline in such a way that if the Checkstyle or PMD gave any warnings for either main (or test classes as well for PMD), then the respective Checkstyle / PMD task would fail, leading to an overall completion of the pipeline with warnings. Moreover, the configuration of the Checkstyle we were using to run the checks locally was not properly configured to ignore test and built classes as well.

### Reaction:
The Checkstyle configuration was appropriately set. We further explored as a team multiple paths to go forward: sticking with the situation we were currently in, preventing PMD partially / completely from being included in the pipeline, keeping everything activated, We agreed to not run these 2 checks on test classes (and built classes), but keep them for main. Further we agreed to individually ensure that our code would pass the tests.





## Adjustments for the next Sprint Plan

For the next sprint, we will go into deeper and more accurate talks regarding implementation to make sure the tasks we are coding follow our chosen design patterns, thus removing the need of refactoring our code later on to resolve the issues. Clear communication will be a priority going forward, as it is necessary to the success of the team. In addition to that, we will better consult with TA’s and ask for feedback to make sure we are on the correct path.
