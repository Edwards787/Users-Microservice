# Main problems encountered
## Problem 1
### Description:
Testing HTTP request calls ended up being harder than expected using simple mocking. We have not figured to use a certain framework and in this way had a lot of problems when testing API calls. Later, when we realized that we tested endpoints improperly, another problem occurred regarding setting up the needed framework as it was not working.

### Reaction:
We were consulting with TAs and online resources of how to install necessary plugins. However, the real problem is that we have not used the plugin in the first place.

## Problem 2:
### Description:
Implementing the factory pattern was more difficult than expected as we had a lot of the base code for the Factory pattern already implemented before we changed it to fit the builder pattern but then we had to change it back.

### Reaction: 
In the future better plan our design patterns, so that we don’t have to refactor as much, and make sure that they fit our use case

## Problem 3:
### Description:
We didn’t know how to implement the getLocation() method for customers as the definition of location for a customer was quite vague. Additionally, the requestRefund() method for customers involved tricky querying the other microservices so we faced problems implementing those.

### Reaction:
We discussed the definition of location with the team as well as the other microservices, so that it best fit their needs when it was used by our microservice. In the end we came to the agreement that the location of a customer should be the coordinates of their home address, since it best matched the use case of the delivery team to get the location of a customer. For the requestRefund Method, we agreed to postpone it till the phase where we were working on integrating the other repositories.

## Problem 4:
### Description:
When implementing the Chain of Responsibility pattern, we created an abstract BaseValidator task, with all the other validators extending from it. As a result, when running our MetricsTree checks, the NOC metric reported some high values.

### Reaction:
The initial reaction was to address the issue directly by merging some related validators together. In this way, we would “fix” the metric, but realistically, on the long term, more and more validators would be added and increase the metric again. Upon further research we found that a high NOC was actually linked to fewer faults, so we decided not to implement the changes we were considering.

## Problem 5:
### Description:
We have decided to refactor all of the validator classes to follow the Chain Of Responsibility design pattern. However, it turned out that by refactoring the way validators are implemented, we also need to refactor all of the endpoints separately. Also, the refactoring caused more than half of the tests to fail, so those had to be refactored too. Similar, but less radical, thing happened with authorization, which was refactored to use Strategy design pattern.

### Reaction:
In the future better plan our design patterns, so that we don’t have to refactor as much, and make sure that they fit our use case.



Adjustments for the next Sprint Plan

When it comes to the tasks we will aim to complete within our final sprint, we will first have to make sure that all the endpoints in our openapi specification are implemented, along with proper testing. Moreover, we will have to look into how we can conduct end-to-end testing, starting with integrating the other microservices into one complete application.
